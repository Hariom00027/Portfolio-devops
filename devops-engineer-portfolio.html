What is a DevOps engineer portfolio?

A DevOps engineer portfolio is a collection of real projects that shows how an engineer builds, ships and runs software. Unlike a resume, it links to working systems, source code and write-ups that explain the decisions behind them. Hiring teams use it to check six things: CI/CD pipelines, infrastructure as code, containers and orchestration, cloud and edge deployments, monitoring and alerting, and security built into delivery.

The sections below follow those six areas. For each one I show the project that demonstrates it, the stack, and where to see the code or the running system.

Flagship project: hosting the Saarthix platform solo

Saarthix needed a production platform with no infrastructure team and no budget for a large managed setup. I designed, deployed and run the whole thing myself. Traffic enters through Cloudflare (DNS, CDN, TLS and WAF), passes a load balancer and an API gateway that act as the single front door, and reaches containerised Spring Boot and React services. A CI/CD pipeline ships every change, and monitoring and alerting let one person keep it healthy.

CI/CD pipelines

What it shows: changes reach production automatically, safely and repeatably. This portfolio is the public example. It's plain HTML, CSS and JavaScript in the Portfolio-devops repository, and every push to main deploys it to Cloudflare in under a minute, with no manual steps.

  • Config as code: security headers, cache lifetimes and redirects live in _headers and _redirects files in the repository, so every change is reviewed in Git.
  • Cache safety: stylesheets and scripts are versioned on each release, so returning visitors never get new HTML with old CSS.
  • Search delivery: a sitemap, structured data and IndexNow notify search engines when pages change.

For Saarthix, the pipeline lints, tests, scans, builds and deploys every change. The pipeline section on the home page walks through each stage.

Infrastructure as code

What it shows: environments are described in files, not clicked together in a console, so they can be reviewed, versioned and rebuilt. In the Saarthi-Test stack the entire environment (three services, their build contexts, ports, start-up order, health check and data volume) is declared in a single docker-compose.yml. On this site, hosting behaviour is versioned in the same way. I also work with Terraform and Ansible; you can see the full list in the skills section.

Containers & orchestration

What it shows: applications packaged once and run the same way everywhere. Saarthi-Test is a test-hosting version of SaarthiX with three containers: a React (Vite) frontend served by Nginx, a Spring Boot (Java 17) API, and MongoDB 6. The API waits until the database passes its health check before it starts, and the data lives on a named volume so it survives restarts.

backend-test:
  build: { context: ./backend, dockerfile: Dockerfile }
  depends_on:
    mongodb-test:
      condition: service_healthy
mongodb-test:
  image: mongo:6
  volumes: [ mongo-test-data:/data/db ]
  healthcheck:
    test: mongosh --eval "db.adminCommand('ping')" --quiet
    interval: 10s
    retries: 5

Excerpt from saarthix-test/docker-compose.yml.

Cloud & edge deployments

What it shows: real systems serving real traffic. Saarthix runs behind Cloudflare, which handles DNS, TLS, caching and the WAF, so most static traffic never reaches the origin. This portfolio is served from Cloudflare's edge with Brotli compression, HSTS and long cache lifetimes for fonts and images. I've also packaged a customer lifetime value model as a Streamlit app with a Procfile and setup script, so it deploys to a platform-as-a-service with a single command.

Monitoring & performance

What it shows: measuring systems instead of guessing. For Saarthix, monitoring and alerting are what make it possible for one person to run the platform. On this site, I measured performance with Lighthouse and fixed the causes rather than the symptoms: forced layouts at start-up, render-blocking third-party fonts and layout shifts. The mobile performance score on the live site went from 35 to between 75 and 86 in my lab runs, and layout shift dropped from 0.238 to under 0.04.

Security built into delivery

What it shows: secure defaults, applied automatically. This site sends HSTS, X-Content-Type-Options, Referrer-Policy, X-Frame-Options and a restrictive Permissions-Policy from version-controlled config, and redirects internal files away from public URLs. On Saarthix, the edge WAF and rate limiting stop abusive traffic before it costs anything, and the API gateway enforces authentication for every route.

FAQ

What should a DevOps engineer portfolio include?

A strong DevOps portfolio covers six areas: automated CI/CD pipelines, infrastructure defined as code, containerised applications, real cloud or edge deployments, monitoring and alerting, and security built into delivery. Each project should state the problem, the architecture, the tools used and the result, with a link to the code or a live system.

What projects are in Hariom Singh's DevOps portfolio?

The main project is the hosting of the Saarthix platform, which I designed and run on my own. Others include Saarthi-Test, a Docker Compose stack with a React frontend on Nginx, a Spring Boot API and MongoDB 6; this portfolio site, deployed from GitHub to Cloudflare on every push; and a machine learning model packaged for one-command deployment with Streamlit and a Procfile.

How is this DevOps portfolio hosted and deployed?

The site is plain HTML, CSS and JavaScript with no build step. Every push to the main branch on GitHub deploys it to Cloudflare in under a minute. It uses Cloudflare headers for security and caching, clean-URL redirects, a sitemap, structured data and IndexNow, and is tuned for Core Web Vitals.
